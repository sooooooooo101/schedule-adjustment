# 日程調整アプリ 設計書（ドラフト）

最終更新: 2026-10-15
状態: ドラフト（未合意の項目は「要確認」と記載）

## 1. 目的

自分（作成者）の日程調整の手間をなくすための個人用ツール。販売・一般公開はしない。

解決したいこと:

- スマホから調整ページを作るのが面倒 → 自然文で頼むだけで候補日を作る
- 回答の入力が長い → 友人もログインなしで、自然文かタップで答えられる
- 確定後の登録が面倒 → ワンタップで Google カレンダー登録・招待・Meet URL 発行

## 2. スコープ

### やること（MVP）

1. 作成者が自然文で依頼し、AI が自分の Google カレンダーの空きと照合して候補日時を出す
2. 候補を確認・修正して調整ページを作り、共有リンクを LINE などで送る
3. 回答者はリンクを開き、名前を入れて回答する（ログイン不要）
   - 自然文で回答（例:「火曜の夜と木曜ならいける」）→ AI が ○△× に変換 → 本人が確認して送信
   - または候補ごとに ○△× をタップ
4. 作成者は回答一覧を見て候補を確定する
5. 確定すると次をまとめて実行する
   - 作成者の Google カレンダーに予定を作成
   - Google Meet の URL を自動発行（任意でオフ）
   - メールアドレスを入れた回答者に Google カレンダーの招待を送信
   - 回答者向けの確定ページに日時・Meet URL・「カレンダーに追加」（Google カレンダー用リンクと .ics）を表示

### やらないこと

- 他人が作った TONTON への自動回答（画面の自動操作は壊れやすく、利用規約上の懸念もあるため）
- Zoom 連携（Meet のみ。必要なら後で URL 手入力欄を足す）
- 作成者アカウントの複数化、一般公開、App Store 配布
- 繰り返し予定、リマインド通知

## 3. 画面と流れ

スマホ縦画面を前提に設計する。ホーム画面に追加して使えるよう PWA にする。

### 作成者側

1. ホーム: チャット風の入力欄が1つと、進行中の調整一覧
2. 入力例:「来週火曜の午後か水曜で、AさんBさんと1時間。Meet付きで」
3. 候補確認: AI が出した候補をカードで表示。削除・時刻修正・追加ができる。タイトルと所要時間、Meet の有無もここで確認
4. 作成: 共有リンクを発行し、共有シート（Web Share API）で LINE などに送る
5. 回答一覧: 候補 × 回答者の ○△× 表。○の多い候補を強調表示
6. 確定: 候補を選んで「この日で確定」→ 予定作成・招待・Meet 発行

### 回答者側

1. リンクを開く → 名前（必須）とメールアドレス（任意、招待を受け取りたい人だけ）を入力
2. 自然文で答えるか、候補ごとにタップで答える
3. 自然文の場合は AI の変換結果を ○△× で表示し、本人が修正してから送信
4. 確定後に同じリンクを開くと確定ページになる

## 4. 構成（案）

| 層 | 採用案 | 理由 |
|---|---|---|
| フロント / API | Next.js（App Router）on Vercel | スマホ向け Web とサーバー処理を1つにまとめられる。無料枠で足りる見込み |
| データベース | Supabase（Postgres） | 無料枠で足りる見込み。管理画面で中身を直接見られる |
| 認証 | 作成者のみ Google ログイン。許可するアカウントを1つに固定 | 回答者はログインなし |
| AI | Claude API（構造化出力で日時を JSON に変換） | 自然文 → 候補日時、自然文回答 → ○△× の2用途。モデルは実装時に費用と精度で選ぶ |
| カレンダー | Google Calendar API（freeBusy で空き取得、events.insert で作成） | Meet は conferenceData で発行、招待は sendUpdates=all |

タイムゾーンは Asia/Tokyo 固定とする。

## 5. データモデル（案）

- events: id, title, duration_min, status（open / confirmed）, confirmed_slot_id, meet_enabled, meet_url, gcal_event_id, created_at
- slots: id, event_id, start_at, end_at
- responses: id, event_id, name, email（任意）, comment, created_at
- answers: response_id, slot_id, value（yes / maybe / no）

共有リンクは推測できない長い ID を使う（例: `/e/{ランダム22文字}`）。

## 6. AI の使い方

### 作成時の解釈

入力: 自然文、今日の日付、作成者の空き時間（freeBusy の結果）
出力: タイトル、所要時間、Meet 有無、候補日時の配列

「来週」「午後」などの曖昧な表現は、解釈結果を候補カードに明示して作成者が確認できるようにする。AI の出力をそのまま確定させない。

### 回答時の解釈

入力: 自然文の回答、候補日時の一覧
出力: 候補ごとの yes / maybe / no

回答者が送信前に必ず確認・修正できる画面を挟む。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 回答ページは誰でも開けるため、AI の API を大量に呼ばれて費用がかかる | 調整ごと・IP ごとの回数制限、入力文字数の上限 |
| Google OAuth アプリを「テスト中」のまま使うと、ログイン状態が約7日で切れる可能性がある（記憶ベース、要確認） | 実装前に Google の一次情報を確認。切れる場合は「本番公開（未審査）」での運用か、定期的な再ログインで割り切るかを決める |
| Google カレンダーを使わない友人がいる | 確定ページで .ics を提供。招待メールは Google 以外のメールアドレスにも届くはず（要確認） |
| AI の日時解釈ミス | 作成時・回答時とも、確定前に人が確認する画面を必ず挟む |

## 8. 未決事項

- 普段の調整は1対1中心か、3人以上中心か（1対1中心なら、候補を作って即確定する近道の流れを足す）
- 構成（Next.js + Supabase + Vercel）で問題ないか
- 作成者の Google アカウントは個人の Gmail か、Google Workspace か（Workspace なら OAuth の扱いが簡単になる可能性がある）

## 9. 実装の順番（案）

1. 雛形作成、作成者の Google ログイン、Supabase 接続
2. 調整の作成（まずは手入力の候補で）→ 共有リンク → 回答 → 回答一覧
3. 確定時の Google カレンダー登録・招待・Meet 発行
4. AI による作成時の自然文解釈（freeBusy 連携込み）
5. AI による回答時の自然文解釈
6. PWA 化、回数制限などの仕上げ
