# 日程調整アプリ 設計書（ドラフト）

最終更新: 2026-10-16
状態: 目標とするプロダクト仕様。現行コードの機能・実装状況は [docs/implementation-status.md](implementation-status.md) を参照。設計書の記載だけで実装済みと判断しない。

## 1. 目的

この文書は目標仕様であり、現在利用できる機能の一覧ではない。機能の実装状態はコードと実装状況文書で照合する。

作成者と参加者がメールアドレスでアプリに登録し、グループの日程調整を行うツール。Google CalendarやSlackはアプリ認証と分離し、利用者が後から任意で連携できる設計にする。販売・App Store配布はしない。

解決したいこと:

- スマホから調整ページを作るのが面倒 → 自然文で頼むだけで候補日を作る
- 回答の入力が長い → メール認証後、自然文かタップで答えられる
- 確定後の登録が面倒 → ワンタップで Google カレンダー登録・招待・Meet URL 発行

## 2. スコープ

### やること（MVP）

1. 作成者が候補日時を手入力、または自然文から作り、内容を確認・修正する。MVPではGoogle Calendarの空き時間を自動取得しない
2. 候補を確認・修正して調整ページを作り、共有リンクをLINEなどで送る
3. 回答者はリンクを開き、メールアドレスでアプリに登録・ログインして回答する
   - 自然文で回答（例:「火曜の夜と木曜ならいける」）→ AIが○△×に変換 → 本人が確認して送信
   - または候補ごとに○△×をタップ
4. 作成者は回答一覧を見て候補を確定する
5. 確定後はアプリ上で日時を表示し、カレンダー登録の代替方法（.icsやGoogle Calendar追加リンクなど）は別チャットの調査結果を受けて決める。MVPの確定処理でCalendar APIは呼び出さない
6. Meet URLは自動発行せず、必要なら作成者が外部会議URLを入力できる方式を検討する

### やらないこと

- 他人が作った TONTON への自動回答（画面の自動操作は壊れやすく、利用規約上の懸念もあるため）
- Zoom 連携（Meet のみ。必要なら後で URL 手入力欄を足す）
- 販売、App Store 配布
- 繰り返し予定、リマインド通知

## 3. 画面と流れ

スマホ縦画面を前提に設計する。ホーム画面に追加して使えるよう PWA にする。

### 作成者側

1. ホーム: チャット風の入力欄が1つと、進行中の調整一覧
2. 入力例:「来週火曜の午後か水曜で、AさんBさんと1時間。Meet付きで」
3. 候補確認: AI が出した候補をカードで表示。削除・時刻修正・追加ができる。タイトルと所要時間、Meet の有無もここで確認
4. 作成: 共有リンクを発行し、共有シート（Web Share API）で LINE などに送る
5. 回答一覧: 候補 × 回答者の ○△× 表。○の多い候補を強調表示
6. 確定: 候補を選んで「この日で確定」→ 予定作成・招待・Meet 発行

### 回答者側

1. リンクを開く → メールアドレスで登録・ログイン → 表示名を入力
2. 自然文で答えるか、候補ごとにタップで回答する
3. 自然文の場合はAIの変換結果を○△×で表示し、本人が修正してから送信
4. アプリ内アカウントの本人は自分の回答を編集・削除できる。確定後の回答は変更できない
5. 確定後に同じリンクを開くと確定ページになる

## 4. 構成（案）

| 層 | 採用案 | 理由 |
|---|---|---|
| フロント / API | Next.js（App Router）on Vercel | スマホ向けWebとサーバー処理を1つにまとめる |
| データベース | Neon（Postgres、Vercel Marketplace経由） | 現行構成を維持する |
| 認証 | メールアドレスを使ったアプリ内認証。具体方式は未決 | Google Workspace OAuth管理ポリシーにアプリの基本利用を依存させない |
| AI | Gemini API（Flash-Lite系、無料枠） | 自然文→候補日時、自然文回答→○△×の2用途。接続部分は差し替え可能にする |
| 外部連携 | Google Calendar / Slackは任意・後付け | 未連携でもMVPの日程調整を完結させる |

タイムゾーンは Asia/Tokyo 固定とする。

### 外部連携の設計方針

- アプリ内ユーザーIDと外部サービスのアカウント・トークンを分離して保存する。
- 連携は設定画面から利用者が明示的に開始・解除できるようにする。
- Google Calendar/Slackごとに必要最小限の権限を要求し、連携できない場合も基本機能を妨げない。
- トークンを保存する場合は暗号化し、ログに記録しない。連携解除時のトークン失効・削除を設計する。
- カレンダー自動登録の具体方式は別途調査・Product Owner決定待ち。

タイムゾーンは Asia/Tokyo 固定とする。

### 任意のGoogle Calendar連携（将来機能）

- 1ユーザーが複数のGoogleアカウントを連携できるかは後続仕様で決める。
- Google Calendarの空き確認・予定作成・Meet発行はMVPに含めない。
- 組織管理者がOAuth連携を許可しない場合、その連携機能だけを利用不可とし、アプリ本体を利用可能にする。

### OAuth スコープ

- アプリ本体の登録・ログインにはGoogle OAuthを使わない。
- Google Calendar連携では、ユーザーが連携操作を開始した時だけ、必要な権限を説明して同意を求める。
- Calendarの権限は利用目的ごとに最小化する。空き時間確認・予定作成・Meet発行を同時に前提とせず、採用する機能ごとに必要scopeを確認する。
- Google Workspace管理者がアプリをブロックまたは未設定としている場合、OAuthを強制せず、手動での日程調整と確定を利用可能にする。
- Google CloudのOAuth Client ID、公開状態、verification、本番設定はNOT VERIFIED。

### UI の方針（TaskDock準拠）

TaskDockの実装済みデザインをWebに合わせて適用する。画面をそのまま複製するのではなく、TaskDockの視覚的なルールと操作の手触りを引き継ぐ。

- **配色:** ライトは明るいシステム背景、ダークは黒〜濃いグレー。主要アクションは地と強いコントラストを持つ無彩色にする。通常の強調に青・オレンジ・緑を散らさない。赤は取り消せない削除など破壊的操作に限定する。
- **文字:** M PLUS 2を固定配信せず、iOS/macOSのシステムフォントを優先して日本語向けフォールバックを指定する。大見出しは詰め、本文は標準字間、小さい補助ラベルは読みやすい行間を取る。
- **面と階層:** システムグループ化リストに近い背景と白/濃色のセクション面を使う。カードを過剰に重ねず、余白・文字の太さ・面積で優先順位を示す。
- **操作:** 画面ごとに主操作を一つ明確にする。作成・確定など重要な操作はスマートフォンで押しやすい位置に固定し、押した瞬間に反応する。候補の○△×は記号と選択面のコントラストで区別し、色だけに意味を持たせない。
- **状態:** 読み込み中、保存完了、警告、エラーを画面上で短く具体的に伝える。破壊的操作は通常操作と色・配置を分け、必要な場合だけ確認を求める。
- **アクセシビリティ:** タップ領域は44px相当以上、キーボードフォーカスを可視化し、色以外の手掛かりを併用する。prefers-reduced-motionに対応する。ライト/ダーク両方で文字と操作のコントラストを保つ。
- **画面密度:** モバイルを主対象にしつつ、広い画面では読みやすい最大幅を保つ。候補タイムラインや回答一覧は横スクロールに依存せず、スマートフォン幅で操作できる形にする。

既存の docs/09_ux.md（TaskDock）と Shared/DesignSystem/Theme.swift のルールを参照元とする。現行Web UIの再設計・実装は別タスクで行い、設計書の記述を実装済みとは扱わない。

## 5. データモデル（案）

- events: id, title, duration_min, status（open / confirmed）, confirmed_slot_id, meet_url（任意）, created_at
- slots: id, event_id, start_at, end_at
- users: id, verified_email, created_at; responses: id, event_id, respondent_user_id（アプリ内ユーザー）, name, email（任意）, comment, created_at（event_id + respondent_user_idで一意）
- answers: response_id, slot_id, value（yes / maybe / no）; user_integrations: user_id, provider, external_account_id, encrypted_tokens, scopes, connected_at

共有リンクは推測できない長い ID を使う（例: `/e/{ランダム22文字}`）。

## 6. AI の使い方

### 段階方式（AI の性能と無料枠の上限をコードで補う）

1. ルールで解釈する：「明日」「来週火曜」「午後」「19時」などのよくある言い方は正規表現と日付計算で処理し、AI を呼ばない
2. ルールで読めなかった場合だけ Gemini に渡す。AI には「来週・火曜・午後・60分」のような中間形式だけを出させ、実際の日時への変換・空き時間との照合はコードで行う
3. AI の出力は zod で検証し、形が崩れていればエラー内容を添えて1回だけやり直す
4. 無料枠の上限に達したら、手入力の画面に切り替える。必要になれば有料の安いモデルを予備に足す
5. 例文と正解の組（数十件）を用意し、モデルの正解率を自動で測る

### AI に渡すデータ

入力文と今日の日付だけ。カレンダーの予定や空き時間は渡さない（Gemini の無料枠では入力が Google の製品改善に使われるため）。無料枠はアプリの API キー単位なので、全ユーザーで共有になる点に注意。ユーザーごとに1日の回数上限を設ける。

### 作成時の解釈

入力: 自然文、今日の日付、作成者の空き時間（freeBusy の結果）
出力: タイトル、所要時間、Meet 有無、候補日時の配列

「来週」「午後」などの曖昧な表現は、解釈結果を候補カードに明示して作成者が確認できるようにする。AI の出力をそのまま確定させない。

### 回答時の解釈

入力: 自然文の回答、候補日時の一覧
出力: 候補ごとの yes / maybe / no

回答者が送信前に必ず確認・修正できる画面を挟む。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 回答ページは誰でも開けるため、AI の API を大量に呼ばれて費用がかかる | 調整ごと・IP ごとの回数制限、入力文字数の上限 |
| OAuth アプリの審査・公開状態が利用可能なユーザー範囲に合わない | 外部の作成者を受け入れる前に、現在のOAuth公開状態、要求scope、審査要件、ユーザー上限をGoogle Cloudの実設定と公式要件で確認する。現時点では未確認 |
| Google カレンダーを使わない友人がいる | 確定ページで .ics を提供。招待メールは Google 以外のメールアドレスにも届くはず（要確認） |
| AI の日時解釈ミス | 作成時・回答時とも、確定前に人が確認する画面を必ず挟む |

### 回答編集・削除

メールで認証されたアプリ内ユーザーは本人の回答を編集・削除できる。サーバー側のアプリ内ユーザーIDで所有者を確認し、名前や回答フォームのメール一致だけで認可しない。確定後は変更不可。既存の匿名回答は新方式の導入時に削除する。詳細は [TONTON型機能仕様](features/tonton-style-scheduling/SPEC.md) を参照。
