# TONTON型候補タイムラインと回答管理 仕様（ドラフト）

状態: Product Owner確認済みの要件と、実装前に判断が必要な項目を分離した実装仕様  
更新日: 2026-10-16  
参照: [TONTON機能比較](../implementation-status.md#tontonを参考にした機能の比較)

## 1. 目的

候補日時を日付ごとの時間帯タイムラインから作成できるようにし、同じ時間帯を複数日に一括適用できるようにする。回答者はログインせずに回答し、後から自分の回答をパスワードで編集・削除できるようにする。

TONTONの画面や内部実装を複製するのではなく、このアプリの既存イベント・候補・回答フローに統合する。

## 2. 決定済み要件

- 候補タイムラインは30分刻み。
- 同じ時間範囲を複数の選択日へ一括適用できる。
- 回答者は登録時に設定したパスワードで自分の回答を編集・削除する。
- 回答者は引き続きログイン不要。
- 対象はこのアプリ内のイベントのみ。TONTONの自動操作・連携はしない。

## 3. 機能要件

### 3.1 主催者: 日付・候補時間の設定

1. イベント作成フォームに複数日を追加・削除する操作を設ける。
2. 各日について、30分刻みのタイムライン上で開始・終了時間を選べる。
3. 選択日を複数指定し、時間範囲を一括適用できる。
4. 一括適用後も各日を個別編集できる。
5. 範囲は開始時刻を含み終了時刻を含まない。既存の所要時間を使い、候補開始時刻から終了時刻までイベント全体が収まる場合だけ候補を生成する。例: 09:00–12:00、所要時間60分なら09:00、09:30、10:00、10:30、11:00。
6. 生成候補は既存の `slots(start_at, end_at)` として保存し、既存の回答集計・確定処理と互換にする。
7. API/Server Action側で候補数上限（現行 `MAX_SLOTS=30`）を再検証する。上限超過時は候補を切り詰めず、どの日・範囲が原因か分かるエラーを出し、送信を拒否する。
8. 日付・時間はAsia/Tokyoで解釈し、DSTに依存しない。
9. 重複する候補日時は保存前に重複排除する。
10. 既存の手入力候補の編集機能がある場合は維持し、タイムラインと矛盾しない形で候補確認・修正ができるようにする。

### 3.2 回答者: 新規回答

1. 名前必須、メール・コメント任意、各候補の○△×という現行入力を維持する。
2. パスワードと確認入力を追加する。送信前に両方が一致し、サーバー側の長さ・形式検証を通ること。
3. 回答・回答内容・パスワードハッシュの保存は一貫したトランザクションで行う。
4. 成功後、回答者に編集・削除用の秘密情報を安全に提示する。既存の整数DB IDを公開の管理識別子として使わない。URLやレスポンスにパスワード、ハッシュ、平文の秘密情報を含めない。
5. 成功後も共有イベントページへ戻れる。ブラウザを閉じても管理識別子とパスワードで再度管理操作を開始できる。

### 3.3 回答者: 編集・削除

1. 回答一覧または送信完了画面から「自分の回答を編集」「自分の回答を削除」へ進める。
2. 管理識別子と登録パスワードを要求する。IDだけ、名前だけ、メールだけでは操作を許可しない。
3. 編集では名前、メール、コメント、全候補の○△×を更新できる。回答行とanswersの変更をトランザクションで保存する。
4. 削除では対象回答とそのanswersのみ削除する。イベント・他回答者の回答は変更しない。削除前に確認画面を表示する。
5. 存在しないID・誤パスワード・対象外イベントは、攻撃者が回答の存在を判別しにくい共通エラーにする。
6. イベント確定後は回答編集・削除を許可しない。確定表示は現行どおり。
7. 成功・失敗時にパスワードや管理識別子をログへ記録しない。パスワードをURLクエリ、分析イベント、エラー文に含めない。
8. 連続した認証失敗を制限する。実装前に既存デプロイ環境で信頼できるレート制限手段を確認する。既存スタックで成立しない場合は新しいサービス・依存を独断で導入せず、実装を止めて提案する。

## 4. データ・セキュリティ要件

- パスワードは専用のパスワードハッシュ方式でハッシュ化し、平文を保存しない。一般的な高速ハッシュ（SHA-256等）で代用しない。
- パスワード値とハッシュを読み取りページのprops/API応答/一覧に含めない。
- 管理識別子は暗号学的乱数で十分なエントロピーを持たせる（推奨128bit以上）。DBには識別子そのものではなくハッシュを保存し、照合時に定数時間比較を行う。DBの連番IDを外部に公開しない。
- すべての認可確認をサーバー側で行う。クライアントが送るevent ID/response IDの組み合わせを信用せず、管理識別子で特定された回答が当該イベントに属することを確認する（IDOR対策）。
- 編集・削除Server ActionはCSRF防御を既存Next.js構成に合わせて確認し、入力スキーマを検証する。
- 試行回数制限は匿名回答者の攻撃に有効で、プロキシ配下のIPヘッダーを無条件に信用しない。IP・識別子等の保存範囲と保持期間を最小限にする。
- 失敗応答は内容・ステータス・処理時間からパスワード一致を推測しにくくする。
- イベント作成者のログインは回答者の編集・削除権限を自動的に与えない。主催者による回答削除は今回の範囲に含めない。
- 個人情報の保管・削除・プライバシー表示に影響するため、実装後にプライバシーページとの整合をレビューする。

## 5. 既存回答と復旧に関するProduct Owner判断（実装前ブロッカー）

既存回答には認証情報がない。過去回答へ推測パスワードを付与したり、平文パスワードを後付けしてはならない。以下はProduct Ownerの決定が必要で、CCが独断で確定してはならない。

- **既存回答の移行:** 推奨案は、旧回答は集計に残し、本人による編集・削除はできない「読み取り専用」とする。旧回答を編集可能にする必要があるなら、本人確認を別途設計する。
- **パスワード忘れ:** メールは任意なので、メールによる復旧は現行前提では保証できない。推奨案はパスワードリセットなしとし、登録時にその制限を説明する。別の復旧方式を望む場合は本人確認を再設計する。
- **回答の重複:** パスワードを忘れた回答者が新規回答を作ることを許すか、同一人物らしさで重複を防止するか。個人情報で重複判定する場合はプライバシー影響を判断する。推奨案は重複回答を許し、名前等による自動統合をしない。

これらの決定が記録されるまで、データ移行を伴う実装を開始しない。

## 6. 受入条件

### タイムライン

- AC-T01: 主催者は複数の日付を登録し、各日の開始・終了範囲を30分単位で選べる。
- AC-T02: 一括適用した時間範囲が選択対象の日付すべてに反映され、適用後に一日だけ個別変更できる。
- AC-T03: 所要時間が範囲に収まる開始候補だけが30分間隔で生成される。終了時刻ちょうどに終了する候補は許可する。
- AC-T04: 生成候補が上限を超えると、サーバーは保存せず明確な検証エラーを返す。候補のサイレント切捨てはない。
- AC-T05: 重複候補を含む入力を送っても各開始日時は一つだけ保存される。
- AC-T06: 保存候補は既存の回答・集計・確定で利用できる。

### 回答管理

- AC-R01: ログインなしでパスワード設定付き回答を登録できる。パスワード不一致・無効入力は保存されない。
- AC-R02: 正しい管理識別子とパスワードの組み合わせで、回答者本人のプロフィール・回答だけを編集できる。
- AC-R03: 誤パスワード、別回答の識別子、改ざんしたイベントIDでは回答を読取・編集・削除できない。
- AC-R04: 削除確認後は当該回答とanswersのみ削除され、集計から反映される。他の回答・イベントは残る。
- AC-R05: 確定済みイベントの回答を変更・削除できない。
- AC-R06: パスワード平文・ハッシュ・管理識別子がHTML、クライアントデータ、URL、ログへ漏れない。
- AC-R07: パスワードは平文保存されず、認証試行は定義済み制限を受ける。
- AC-R08: 旧回答の取扱いと忘れた場合の案内が、決定されたProduct Owner方針どおり動く。

## 7. 実装・レビュー手順

1. Product Ownerが第5節の3項目を決定する。
2. Claude Codeは現行のフォーム、Server Action、validation、DB migration、イベント状態遷移、ホスティング設定を読み、仕様の不整合を先に報告する。
3. 匿名回答の本人確認・認可変更のため、実装前にAntigravityの独立セキュリティ/アーキテクチャレビューを受ける。
4. レビュー指摘を設計へ反映してからClaude Codeが実装・テストする。
5. Codexが要件適合とArchitecture Driftを確認し、Antigravityが独立再レビューする。PR merge/deployはProduct Owner判断。

## 8. Claude Code実装引継ぎ

### Objective
30分刻みの候補タイムライン、一括時間設定、回答者自身によるパスワード保護付き回答編集・削除を、既存アプリへ追加する。

### Context / Relevant Files
- 現行実装を再確認する: `src/app/events/new/`, `src/app/e/[id]/`, `src/app/events/actions.ts`, `src/lib/events.ts`, `src/lib/validation.ts`, `db/migrations/`, `src/app/events/_results.tsx`
- 目標仕様: この文書と `docs/design.md`
- 状況の根拠: `docs/implementation-status.md`

### Constraints
- 仕様にない重大な設計判断、依存追加、外部レート制限サービス追加、認証モデル変更をしない。
- 第5節のPO判断とAntigravity事前レビューが完了するまで、認証・Migrationコードを書き始めない。
- まず既存コード・DB・デプロイ環境との差をまとめ、仕様と矛盾する場合は実装を止めて提案する。
- DB migrationは追加的かつロールバック可能な案を示し、既存回答のデータ損失を避ける。
- タイムラインはフォーム入力支援であり、サーバーで候補の重複、上限、日時、durationを必ず再検証する。

### Security
第4節の全項目を必須要件とする。新規パッケージや認証・レート制限方式に曖昧さが出たら実装せず提案する。

### Required Tests
実装時にVitest等の既存テスト構成へ、時間範囲からの候補生成、上限・重複・境界値、認証成功/失敗、別回答IDへのアクセス、削除範囲、確定後拒否、レート制限を検証するテストを追加する。テストはClaude Code実装時の必須成果物。

### Definition of Done
全ACがPASSし、Migrationの適用/ロールバック方針が確認でき、プライバシー表示をレビューし、Antigravityの独立レビュー指摘が解消または明示的に受容され、CodexのArchitecture Drift Reviewが完了している。
